## Product design

### Goals / Non-goals

**Goals (v1 — this ticket):**
- Give an MCP-compatible AI client (via the Agent Platform gateway) read access to a connected HighLevel sub-account's core CRM data: contacts, sales opportunities/pipelines, calendar appointments, and conversations.
- Give it limited, auditable write access on the one resource that benefits most from AI assistance without being destructive: contacts — create a contact, update a contact's fields, add a note, add tags. Every write is "every action logged" per the ticket's own ask; MSPbots's gateway/platform owns the audit log, this connector just needs to use the Header-scoped, per-request credential model that makes a clean audit trail possible (SOP §3).
- Credentials are supplied per request via HTTP headers (Private Integration Token + Location ID), never stored by the connector, consistent with the platform-wide contract.

**Non-goals (this ticket):**
- Payments/invoicing tools (money-moving — higher risk, needs a deliberate scoping discussion and a real test account before committing to a contract; HighLevel exposes this as a separate API surface).
- Webhook subscription management (receiving HighLevel webhooks requires a stateful subscription + public callback endpoint — a different architecture than a stateless request/response MCP tool; out of scope for a first version).
- Delete/destructive-mutation tools of any kind (no delete-contact, no delete-opportunity, etc.) — matches SOP §2.7 ("write/delete tools must state business necessity, accept only explicit resource IDs, never vague batch deletes"); nothing in this ticket asks for deletion.
- OAuth 2.0 marketplace-app flow — the Private Integration Token path covers the "connect my own HighLevel account" use case this ticket describes; OAuth would only be needed if MSPbots later wants to publish this as a listed HighLevel marketplace app for third parties (see Decisions, below).
- Bulk/batch mutation tools (e.g. bulk tag assignment, bulk contact import) — not asked for, and would need pagination/rate-limit handling well beyond a v1.

### Acceptance criteria AC1..AC10

Given/When/Then; "the agent" = any MCP client calling tools through the gateway with HighLevel credentials attached.

- **AC1 (discovery)**: Given valid HighLevel credentials are attached to the request, When the agent calls `tools/list`, Then it receives the full HighLevel tool set (contacts, opportunities, calendar, conversations — see Tech design §4), with every read-only tool marked `readOnlyHint: true`.
- **AC2 (missing credentials)**: Given a request with one or both required credential headers missing, When any HighLevel tool is called, Then the server returns HTTP 401 with a body naming the missing header(s) — not a 500, not a silent pass-through.
- **AC3 (empty result, read)**: Given valid credentials, When the agent calls `highlevel_search_contacts` with a query that matches no contacts, Then the tool returns an empty list, not an error.
- **AC4 (not found)**: Given valid credentials, When the agent calls `highlevel_get_contact` with a contact ID that does not exist in that sub-account, Then the tool returns the structured `not_found` error envelope, not an exception or 500.
- **AC5 (upstream rate limiting)**: Given valid credentials, When the upstream HighLevel API responds 429 to a tool's request, Then the connector retries with backoff per policy (§7 Non-functional) and, if still failing, returns the structured `rate_limited` error — never a raw passthrough of the vendor's response shape.
- **AC6 (multi-tenant isolation, backend-enforced)**: Given two concurrent requests carrying two different sub-accounts' credentials (Location A and Location B), When both call `highlevel_search_contacts` at the same time, Then each response contains only its own Location's contacts — verified by making the actual two calls and diffing the result sets (not by UI/menu visibility, there is no UI here).
- **AC7 (write + read-your-write)**: Given valid credentials, When the agent calls `highlevel_create_contact` with the required fields, Then a new contact is created in HighLevel and the tool returns its ID; When the agent then calls `highlevel_add_contact_note` with that ID, Then the note is attached and is visible when the contact is re-fetched.
- **AC8 (empty calendar)**: Given valid credentials, When the agent calls `highlevel_list_appointments` for a date range that has no events, Then the tool returns an empty list, not an error.
- **AC9 (pagination / token economy)**: Given a list-type tool call (e.g. `highlevel_search_contacts`) whose result set exceeds the default page size, When the agent omits `limit`, Then the tool returns at most 50 items and sets `has_more: true` with an opaque cursor the agent can pass back; When the agent requests more than the hard cap, Then the tool caps the response at 200 items rather than returning an unbounded list.
- **AC10 (tag/update roundtrip)**: Given valid credentials and an existing contact, When the agent calls `highlevel_update_contact` to change a field and `highlevel_add_contact_tags` to add a tag, Then both changes are reflected when the contact is re-fetched.

Build a new MCP server in the existing empty scaffold `MSPbotsAIFramework/highlevel-mcp`, Python 3.12 + uv + FastMCP per SOP §9 (the house pattern for every other vendor-mcp repo in the org). ### Data & API contract

**Inbound (Agent → this MCP), credential headers:**

| Header | Required | Type | Meaning |
|---|---|---|---|
| `X-HighLevel-Private-Token` | yes | password | HighLevel Private Integration Token, generated in the target sub-account's Settings → Private Integrations |
| `X-HighLevel-Location-Id` | yes | str | The HighLevel sub-account (Location) ID this token is scoped to |

Missing either → `401`, body: `{"error": {"code": "not_configured", "message": "missing required header(s): X-HighLevel-Private-Token, X-HighLevel-Location-Id", "retryable": false}}`.

**Outbound (this MCP → HighLevel API)**: `Authorization: Bearer <token>`, a fixed API-version header (exact current value confirmed against the live docs at implementation time — Open Questions), base URL and per-resource paths likewise confirmed against the live docs at implementation time (not re-derived here from training-era memory, to avoid shipping a wrong literal into a contract section).

**Tool catalog (12 tools, `<vendor>_<verb>_<resource>` naming per SOP §2.8):**

| Tool | Read/Write | Params (abridged) | Returns (abridged) |
|---|---|---|---|
| `highlevel_search_contacts` | read | `query?`, `tag?`, `limit?` (≤200, default 50), `cursor?` | `{contacts: [...], has_more, cursor}` |
| `highlevel_get_contact` | read | `contact_id` | `{contact}` or `not_found` |
| `highlevel_create_contact` | write, not destructive | `name` or `email`/`phone` (at least one identifier), optional fields | `{contact_id}` |
| `highlevel_update_contact` | write, not destructive | `contact_id`, fields to change | `{contact}` |
| `highlevel_add_contact_note` | write, not destructive | `contact_id`, `note_text` | `{note_id}` |
| `highlevel_add_contact_tags` | write, not destructive | `contact_id`, `tags: [str]` | `{contact_id, tags}` |
| `highlevel_list_pipelines` | read | — | `{pipelines: [{id, name, stages: [...]}]}` |
| `highlevel_list_opportunities` | read | `pipeline_id?`, `stage_id?`, `contact_id?`, `limit?`, `cursor?` | `{opportunities: [...], has_more, cursor}` |
| `highlevel_list_calendars` | read | — | `{calendars: [{id, name}]}` |
| `highlevel_list_appointments` | read | `calendar_id?`, `start_date`, `end_date`, `limit?`, `cursor?` | `{appointments: [...], has_more, cursor}` |
| `highlevel_list_conversations` | read | `contact_id?`, `status?`, `limit?`, `cursor?` | `{conversations: [...], has_more, cursor}` |
| `highlevel_get_conversation_messages` | read | `conversation_id`, `limit?`, `cursor?` | `{messages: [...], has_more, cursor}` |

Error envelope (all tools, SOP §4.2): `{"error": {"code": "<one of the fixed vocabulary>", "message": "...", "retryable": bool}}`. Empty results return `{"...": [], "has_more": false}`, never `not_found`.

**Backward compatibility**: new repo, no existing clients to break. Any post-v1 change to a tool name, required param, or Header name is a breaking change and must follow SOP §13 (advance notice, not a silent release).

### Key flow / sequence

```
Agent → Gateway → highlevel-mcp POST /mcp (tools/call highlevel_search_contacts, Headers: token + location id)
  highlevel-mcp: middleware reads headers → ContextVar → 401 early-return if missing
  highlevel-mcp: client.py builds HighLevel request (Authorization, Version, locationId) → GET upstream contacts endpoint
  HighLevel API: 200 with results | 404 | 429 | 5xx
  highlevel-mcp: maps to {contacts, has_more, cursor} | not_found | rate_limited (after backoff) | upstream_error
  highlevel-mcp → Gateway → Agent: structured JSON result or error envelope
```

### Non-functional

- **Idempotency & concurrency**: no idempotency keys on HighLevel's documented API (to be confirmed at implementation time); `highlevel_create_contact` is not idempotent by design — callers that retry on timeout may create a duplicate contact. This is the same risk profile as the vendor's own API; not solved at the connector layer for v1. Request-level isolation (SOP §3.3/§3.4) means two concurrent calls never share credentials or cached state.
- **Performance**: connect/read timeouts 5s/30s, bounded retry with backoff on 429/5xx (`Retry-After` respected), single call budget < 120s, one HTTP client reused per request (SOP §5). List tools default to small pages (≤50) to keep responses token-cheap.
- **Security**: credentials only from headers, never logged, never written to disk or env; `gitleaks detect` run before every merge (SOP §11). No cross-tenant data exposure — the only state is the per-request `ContextVar`, reset in `finally`.
- **Multi-tenant isolation**: every call to the upstream API is explicitly scoped to the `X-HighLevel-Location-Id` from the current request; there is no shared cache keyed by anything other than the current request, so a second tenant's call can never see the first tenant's result. Covered by AC6.
- **Observability**: log tool name, outcome (success/error code), and latency per call; never log the token or location ID value, never log full response bodies (may contain PII — contact emails/phones).

### Risks & dependencies

- **Risk**: wire-level API details (base URL, paths, `Version` header) are confirmed only at implementation time, not in this document. Mitigation: the dev leg reads HighLevel's live docs directly (SOP's own build method — "clean-room... from official API docs"); the tool catalog and contract shapes above are vendor-detail-agnostic (they describe MSPbots-side tool names/params, not HighLevel's literal endpoints), so a wrong guess here would not have changed them.
- **Risk**: Private Integration Token scoping assumption (one token = one Location) may be wrong for some account configurations. Mitigation: `X-HighLevel-Location-Id` is required regardless (Open Questions), so the contract does not need to change even if the assumption is wrong.
- **Dependency**: none on another ticket or unmerged PRD. No gateway/control-plane change needed.
- **Dependency**: a real HighLevel sandbox Location + Private Integration Token, to run the "needs a real vendor account" test cases and to do a real end-to-end verification before any tenant actually connects. Not a blocker for development or INT publish (SOP "no test account is not a blocker").

### Decisions made by DEV01

No one was available to ask (unattended design run); these are the first-version choices made unilaterally, each with the alternative that was not picked:

- **Private Integration Token over OAuth 2.0 marketplace app** — simpler, no app-review wait, matches the platform's Header-only credential contract directly, and satisfies the ticket's literal ask ("connect it... give AI live access"). Alternative not chosen: OAuth 2.0 marketplace flow — needed only if MSPbots wants to be a *listed* HighLevel app, which nothing in the ticket asks for.
- **Require `X-HighLevel-Location-Id` as a second mandatory header, even though it may be redundant if a Private Integration Token is already Location-scoped** — safe in both cases, avoids a design that silently breaks if the assumption about token scoping turns out to be wrong. Alternative not chosen: omit it and assume the token alone is always sufficient — would require a contract change (and possibly a breaking one, per SOP §13) if that assumption turned out false.
- **v1 covers contacts (read + 4 light-touch writes), opportunities/pipelines (read), calendar (read), conversations (read) — 12 tools total; payments, webhooks, OAuth-app listing, and bulk/delete operations are explicitly out of scope** — keeps the connector's risk surface (money, stateful webhook subscriptions, destructive deletes) out of a first version with no real test account yet, while still covering every resource family the ticket's own description names ("contacts, opportunities, calendar, conversations"). Alternative not chosen: full parity with all of HighLevel's documented capability areas in v1 — unbounded scope for a ticket with no vendor account to validate money-moving or destructive operations against.
- **No delete tools of any kind** — per SOP §2.7 (write/delete tools must state necessity and take only explicit IDs, never vague batch operations); nothing in the ticket's ask requires deletion. Alternative not chosen: include delete-contact/delete-opportunity for completeness — rejected as unnecessary risk for a connector whose stated purpose is giving an AI "live access," not data cleanup.
- **Uniform `limit`/`cursor` pagination contract on every list tool regardless of HighLevel's actual pagination mechanism (cursor- or page-based)** — keeps the tool-facing contract stable and token-cheap (SOP §2.5) even if the implementation underneath has to translate to whatever the vendor's real API offers. Alternative not chosen: expose the vendor's native pagination parameters directly — would leak implementation detail into the tool contract and make a future vendor-side pagination change a breaking change for agents.

To change any of these, say so in a comment and move this ticket back to `5b - ready for groom`.
